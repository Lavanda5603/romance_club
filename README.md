# Клуб Романтики

Логин храню и сравниваю с учётом регистра: `Player` и `player` — разные логины. Уникальность проверяет индекс `player_login_unique` в базе, поэтому два одновременных запроса не создают одинаковые аккаунты. Если в перенесённой базе уже есть дубликаты, миграция останавливает запуск с `PLAYER_LOGIN_DUPLICATES`. Такие аккаунты не удаляю автоматически: сначала нужно проверить их владельцев и изменить повторяющиеся логины, сохранив ID и связанные данные.

Я делаю мобильную визуальную новеллу на Dart и Flutter. В игре можно читать эпизоды, выбирать действия персонажей и сохранять прогресс. Также есть регистрация, профиль и редактор эпизодов.

Клиент у меня написан на Flutter, сервер — на Rust, а данные хранятся в SurrealDB. Для запросов между приложением и сервером использую gRPC и Protobuf.

## Как устроен проект

Экраны приложения лежат в `lib/screens`. В `lib/src/domain` находятся модели и интерфейсы репозиториев, а в `lib/src/data` — работа с сервером. Логику прохождения и переходов между сценами я вынесла в `lib/src/features/game`.

В `lib/services/storage_service.dart` храню локальные настройки и данные входа. Файлы в `lib/generated` получены из Protobuf-контрактов из папки `protos`.

Код сервера находится в `server/src`. В `server/migrations` описаны таблицы базы, а в `assets` лежат локальные картинки.

Удаление картинок в обоих API выполняю через отдельное подключение SurrealDB. Оно может читать и удалять только ассеты. Служебный пароль создаю при запуске сервера, в базе сохраняю его хеш. Перед удалением проверяю полный ID записи и таблицу `asset`; если картинки уже нет, возвращаю ошибку, а не сообщение об успешном удалении.

## Как приходят данные

В магазине сервер сам определяет товар, цену и результат покупки по SKU. Подписка `subscription` стоит 500 алмазов, существующий эпизод `episode:<номер>` — 100. Для тестового пополнения доступны только `diamonds_100`, `diamonds_250` и `diamonds_500`; неизвестные товары и неверные типы отклоняются. Активную подписку показываю только после подтверждения права сервером, в том числе после покупки. Старые записи с неправильным типом не дают подписку и не удаляются из базы.

Приложение обращается к серверу на порту `50051`. Сервер подключается к SurrealDB по адресу `127.0.0.1:8000/rpc`. Использую namespace `romance_club` и database `main`.

Когда игрок открывает эпизод, приложение отправляет запрос `GetEpisode`. Сервер читает из базы эпизод, его сцены, выборы и действия, собирает ответ и отправляет его клиенту. После этого приложение показывает сюжет.

## Как я запускаю проект

Сначала открываю PowerShell в папке проекта и запускаю базу:

```powershell
surreal start --user root --pass root --bind 127.0.0.1:8000 surrealkv://database
```

Это окно оставляю открытым. В другом окне запускаю сервер:

```powershell
cd C:\flutter_projects\romance_club\server
$env:SURREAL_NAMESPACE = 'romance_club'
$env:SURREAL_DATABASE = 'main'
$env:GRPC_BIND = '127.0.0.1:50051'
$env:JWT_SECRET = (Get-Content ..\.local\jwt-secret.txt -Raw).Trim()
cargo run
```

Если сервер уже собран, могу запустить `start-server.cmd` из корня проекта.

Затем запускаю Android-эмулятор, жду домашний экран и открываю приложение через F5 в VS Code. Через терминал из корня проекта запуск такой:

```powershell
flutter pub get
flutter run
```

В клиенте указан адрес `10.0.2.2` — через него Android-эмулятор обращается к моему компьютеру. При запуске на телефоне нужен адрес компьютера в локальной сети.

## Изображения

При загрузке сервер сохраняет исходник и готовит размеры для приложения. В сетку идут PNG-превью до 160 пикселей. Для фонов создаются варианты шириной до 720, 1080 и 1440 пикселей, для персонажей — до 512 и 1024 по длинной стороне. Маленькие картинки не увеличиваются, пропорции сохраняются. Непрозрачные фоны сжимаются в JPEG с качеством 82, картинки с прозрачностью и персонажи сохраняются в PNG.

Перед запуском API сервер заполняет отсутствующие превью старых картинок порциями по 24 записи, сохраняя оригиналы. Статус и версия исходника сохраняются в базе: повреждённые или отсутствующие файлы не обрабатываются повторно при каждом открытии сетки. Такую картинку можно загрузить заново. Для старых записей, добавленных после запуска, остаётся ограниченная подготовка превью запрошенной страницы.

Старые JPEG-превью персонажей пересоздаю из оригиналов в PNG, чтобы вернуть прозрачность. Готовую картинку не заменяю, если исходник или превью изменились во время обработки.

Игра передаёт физический размер экрана и получает наименьший подходящий вариант. Если такого размера нет, сервер возвращает самый большой из готовых. Редактор может отдельно запросить оригинал. Обработка идёт в фоновых CPU-задачах, одновременно не больше двух. Оригинал, превью и размеры новой картинки публикуются вместе. Для старых картинок экранные размеры готовятся при первом запросе и сохраняются в базе.

Перед сохранением проверяются содержимое и полное декодирование PNG/JPEG. Максимальный размер файла — 5 MiB, каждая сторона — до 8192 пикселей, суммарно — до 16 миллионов пикселей и 64 MiB декодированных данных. Принимается только один статичный кадр, APNG отклоняется. Ожидание свободного обработчика ограничено 5 секундами, обработка — 20 секундами. При отказе картинка не записывается; уже начатая CPU-задача удерживает свой слот до завершения.

## Что нужно для сборки

Для клиента нужны Flutter и Android SDK. Для сервера — Rust, MSVC и компилятор Protobuf `protoc`. Версия Rust указана в `server/rust-toolchain.toml`. Сейчас использую SurrealDB 3.3.0 и Dart 3.13.2.

Миграции создают таблицы, но не добавляют сюжет. На другом компьютере данные загружаются из SQL-выгрузки SurrealDB с расширением `.surql` через команду `surreal import`.

## Ключ для токенов

Повторные попытки входа и регистрации ограничиваю до чтения базы и Argon2. С одного IP допускаю 30 запросов за 60 секунд, из них регистраций — не больше 5. Для каждого логина и операции действует предел 20 попыток за 60 секунд и 5 попыток за 30 секунд с одного IP. Отклонённые запросы не продлевают окно; постоянную блокировку аккаунта не записываю. В ответе указываю, через сколько секунд повторить запрос. IP беру из TCP-соединения, заголовку `X-Forwarded-For` не доверяю.

Счётчики общие для процесса сервера, их не больше 20 000; истёкшие записи очищаю, при перезапуске счётчики сбрасываются. Максимальный размер входящего сообщения AuthApi — 4 KiB, логина — 64 байта, email — 254 байта, пароля — 1024 байта. Проверки не затрагивают обычные запросы игры с действующим токеном.

Argon2 при регистрации и входе запускаю через общий ограниченный пул `spawn_blocking`. Одновременно выполняются два вычисления, ещё восемь запросов могут ждать до 10 секунд. При переполнении или долгом ожидании сервер возвращает понятную ошибку с предложением повторить запрос. Отмена RPC не освобождает слот уже начатого вычисления до его фактического завершения. Формат хешей, параметры Argon2 и случайная соль остаются прежними.

JWT_SECRET передаю серверу через окружение. Ключ должен быть случайным, не короче 32 байт и без пробелов. Без него сервер не запускается. Ключ не добавляю в Git и не включаю в архив для сдачи.

На новом компьютере создаю отдельный локальный ключ из корня проекта:

```powershell
New-Item -ItemType Directory -Force .local | Out-Null
$jwtBytes = New-Object byte[] 32
$jwtRandom = [Security.Cryptography.RandomNumberGenerator]::Create()
$jwtRandom.GetBytes($jwtBytes)
$jwtRandom.Dispose()
$jwtSecret = [BitConverter]::ToString($jwtBytes).Replace('-', '').ToLowerInvariant()
[IO.File]::WriteAllText((Join-Path (Get-Location) '.local\jwt-secret.txt'), $jwtSecret)
```

start-server.cmd читает этот файл, если JWT_SECRET ещё не задан в окружении. При замене ключа старые токены перестают работать, нужно войти в приложение заново. Аккаунты и прогресс остаются в базе.

После общего сброса увеличиваю поколение прогресса игрока. Каждое сохранение передаёт загруженное поколение, а сервер проверяет его в одной транзакции с записью. Поэтому задержанный запрос не возвращает старый прогресс даже у эпизода без прежнего сохранения. После такого конфликта нужно заново открыть эпизод.

Пакеты diamonds_100, diamonds_250 и diamonds_500 бесплатно начисляют валюту только в учебном демо. Реальные платежи не подключены; эти запросы не подтверждают оплату. Для настоящей продажи валюты начисление должно выполняться после серверной проверки платежа.

Баланс храню в пределах от 0 до 2 147 483 647. Недопустимый SKU, повреждённый баланс и переполнение не меняют кошелёк или историю покупок; повтор одного запроса не начисляет пакет повторно.

Применённые миграции записываю в schema_migration вместе с контрольной суммой. Изменение схемы и запись версии выполняются в одной транзакции; при ошибке сервер не запускает API. При повторном старте применяются только новые файлы. Уже применённые файлы не редактирую — для следующих изменений добавляю новую миграцию.

Окончания строк и пустые строки в применённых миграциях тоже входят в контрольную сумму. Их сохраняю без изменений: автоматическую уборку оформления к этим файлам не применяю.

Миграция 023 переносит старые числовые и строковые переходы в постоянные ключи сцен, сохраняя исходные поля и уже записанные ключи. Пустой переход и числовой 0 остаются концом эпизода.
