## Что я усилила

- Перед сохранением и удалением эпизодов, загрузкой и удалением ассетов проверяю текущую роль игрока в БД. Старого JWT с `is_admin=true` недостаточно после снятия роли или удаления аккаунта. При недоступной БД операция изменения контента отклоняется.
- Сервер по умолчанию слушает `127.0.0.1:50051`. В `start-server.cmd` сохраняю явно заданный `GRPC_BIND`; новый `start-database.cmd` запускает существующую БД на `127.0.0.1:8000`. Эмулятор подключается через `10.0.2.2`. Уже запущенные процессы от изменения файлов не перенастраиваются.
- Отключила обычное резервное копирование Android-приложения через `android:allowBackup=false`, чтобы не включать сохранённую сессию в облачную резервную копию приложения.
- Ограничила состояние прогресса: до 256 флагов и 256 счётчиков, ключи до 128 байт, ссылка сцены и название концовки до 256 байт. Ограничила ключ повторного запроса покупки до 128 байт.
- Запрещаю создавать достижения с неизвестными названиями. Разрешены `all_episodes`, `all_endings`, `max_points`, `secret_scene`, `all_friends`.
- Ограничила очередь обработки изображений восемью задачами вместе с работающими; одновременно обрабатываются две картинки. При заполнении очереди возвращаю `ResourceExhausted`. Место работающей задачи освобождается после её фактического завершения, включая отмену RPC.
- Ограничила длину метаданных загружаемых изображений. Проверки PNG/JPEG, анимации, размеров, числа пикселей и памяти декодирования сохраняются.
- Обновила JWT и TLS-зависимости по опубликованным предупреждениям. Использую JWT с backend `aws_lc_rs`, не добавляя библиотеку RSA для неиспользуемых алгоритмов.

Источники предупреждений: [OSV](https://google.github.io/osv.dev/api/), [jsonwebtoken](https://github.com/Keats/jsonwebtoken/security/advisories/GHSA-h395-gr6q-cpjc), [RustSec](https://rustsec.org/advisories/).

## Что проверяю тестами

Первый полный серверный прогон: 49 тестов прошли, включая отдельные тестовые БД. Проверяю атомарность покупок, конфликты сохранений и сброса, уникальность логина, каскадное удаление, ограничения прав и record ID, откат при ошибках SQL, миграции и подготовку старых изображений.

После изменений добавлены проверки отзыва роли и удаления администратора в отдельной БД, отказа неизвестным достижениям и большим запросам до обращения к БД, вместимости очереди изображений. Повторный прогон после окончательных JWT/TLS/Tokio: 50 тестов прошли; длительный тест каталога и оригиналов отдельно прошёл в первом полном прогоне и в этом повторе пропущен. Все 246 тестов Flutter прошли.

Проверка OSV выявила также `RUSTSEC-2026-0386` для Unix API Tokio: обновила `1.53.1` до `1.53.3`. Предупреждение `RUSTSEC-2023-0089` относится к неподдерживаемому `atomic-polyfill` в lock-файле; `cargo tree -i atomic-polyfill` не показывает его в дереве текущей Windows-сборки. Это остаётся замечанием для других платформ, а не подтверждённой атакой на текущую конфигурацию.

Окончательный запрос OSV проверил 460 записей зависимостей из Cargo.lock и pubspec.lock. Осталось только указанное предупреждение о неподдерживаемом atomic-polyfill; это проверка известных записей каталога на текущую дату, а не гарантия отсутствия неизвестных проблем.

Пользовательскую БД не использую для записей тестов. Тесты создают базы со случайными именами и удаляют только свои базы. Запущенную игру и сервер для применения изменений не останавливаю.

## Что остаётся ограничением

- Перед публикацией сервера в сети нужны TLS, отдельная учётная запись БД с минимальными правами и отказ от демонстрационных `root/root`. Локальный bind ограничивает доступ, но не заменяет эти меры для сетевого размещения.
- Прогресс приходит от клиента. Взломанный клиент может подделывать собственные баллы и прохождение; сервер проверяет владельца, принадлежность сцены эпизоду и версии записи, но не пересчитывает всю историю выборов. Для соревновательной игры или платных наград нужна серверная логика прохождения.
- Пополнение валюты остаётся бесплатной демонстрационной возможностью, а не настоящей платёжной системой.
- Сессия хранится в файле в каталоге приложения. Защита от извлечения токена с уже скомпрометированного устройства не подтверждена; для этого требуется хранилище с ключом Android Keystore.
- Ограничение времени обработки изображения проверяется между стадиями. Оно не прерывает декодер посреди одного синхронного вызова; пределы пикселей, памяти и числа рабочих задач ограничивают его ресурсы.
- Полный внешний пентест, нагрузочный тест и обновлённый release APK в рамках этой проверки не подтверждены.

## Оформление и запуск

Убираю завершающие пустые строки в текстовых файлах проекта. Все 28 применённых миграций исключены: контрольные суммы совпадают с сохранёнными значениями, окончания строк в них не меняю. Каталоги сборок, БД, Git и локальные секреты не форматирую. В настройках VS Code отключено восстановление позиции при повторном открытии файла; это не перемещает курсоры уже открытых вкладок.

`flutter analyze --no-pub` завершился без замечаний; отдельная проверка `lib`, `test`, `integration_test` также прошла. Проверка `git diff --check` не нашла ошибок оформления diff.

После окончания ручной проверки останавливаю старый сервер через Ctrl+C и запускаю `start-server.cmd` из корня проекта: он сам пересобирает изменения через `cargo run --locked`. Для локального запуска БД использую `start-database.cmd`. Одновременно второй экземпляр БД с той же папкой `database` не запускаю.
